## 1. 项目背景与真正目标

我正在研究一套**逻辑驱动的 AI 学习与推理系统**，目标不是传统规则引擎，也不是简单为大语言模型外挂一个知识库。

拟研究的核心能力包括：

- 将概念、知识断言、证据、假设、推理规则和证明过程显式表示；
- 对未知问题生成多个候选猜想，并通过查询、实验、运行代码等手段验证；
- 记录正反证据与错误经验，保证“未知不等于错误”；
- 将知识模型、行动模型、学习策略分离；
- 通过学习减少相似问题的搜索成本，必要时引入小型神经网络，而非每一步都依赖大模型逐 Token 输出；
- 初期使用 Kotlin 实现易读、易修改的学习/推理原型，未来只将有明确性能瓶颈的部分重构为 Rust。

**开发者的第一约束是可读性和可理解性**：希望自己能直接读懂每一个知识对象、推导步骤及程序行为。因此探索中文 Kotlin 方言，包括中文标识符、部分中文关键字和全角标点。

这引出两个不同但相关的需求：

**A. 中文 Kotlin 开发工具**：让我能高效、正确地编写和调试 `.ktzh` 代码。  
**B. AI 学习与推理调试器**：让我能观察 AI 实际执行了哪些检索、推导、猜想、验证和知识更新。

A 是开发生产力工具；B 是 AI 研究基础设施。两者应共享工作区，但不能设计成强耦合的一体式系统。

## 2. 已有工作：不要重复造轮子

以下为现有《中文方言设计-v0.1.md》**所报告的实现与测试**，不是本建议文档重新复测的结论：

- 使用 `.ktzh` 扩展名启用文件级中文方言；普通 `.kt` 文件保持标准 Kotlin；
- 已有 Python 转译器 `ktzh.py`，可以把中文方言转成标准 `.kt`；
- 第一批支持 13 个关键字：`函数/值/变量/如果/否则/只要/遍历/当/在/返回/真/假/空`；
- 全角标点使用显式白名单映射，不做全局 NFKC 归一化；
- 词法状态区分普通代码、字符串、原始字符串、字符、行注释、嵌套块注释、字符串模板；
- 已实现逐字符位置映射，以及部分编译错误的位置回映射；
- 文档报告了编译、运行、回映射和存量 `.kt` 零回归测试；
- 目前**没有** `.ktzh` 在 IntelliJ 中的完整智能补全、重构和增量构建；错误回映射的代码片段/caret 仍可能错位。

另据《认知陈述-v0.1.md》，必须警惕：**中文关键字是否真正提高理解速度尚未被验证**；不要把“实现中文语法 Demo”误认为“提升逻辑 AI 研究效率”。

原则：先复用已经可工作的转译器，不先 fork Kotlin 编译器，更不先自研数据库或新的通用 IDE 内核。

## 3. 推荐方案：先做 VS Code 扩展，不做独立 IDE

建议路线：

```text
                VS Code / Code-OSS（现成编辑器）
                            │
                中文 Kotlin 扩展（TypeScript）
                 ┌──────────┴──────────┐
                 │                     │
         .ktzh 语言支持          AI 推理调试视图
                 │                     │
         转译器 + source map      事件流/状态快照/回放
                 │                     │
       标准 .kt / Kotlin LSP      Kotlin 学习与推理引擎
                 │                     │
             Gradle/JVM               知识存储
```

### 3.1 中文代码编辑部分

第一阶段只开发 VS Code 扩展：

- 注册 `.ktzh` 文件类型、语法高亮、括号匹配、自动缩进、中文关键字片段；
- 提供“转译/编译/运行/查看生成 Kotlin”命令；
- 把编译诊断定位到原始 `.ktzh`，显示中文源码片段和正确光标位置；
- 为生成文件提供明确标识：**只读、不可作为权威源文件**；
- 保留中文/标准 Kotlin 对照查看功能，辅助理解和学习。

TypeScript 只用于 IDE 扩展。**不要求把已经实现的 Python 转译器改写成 TypeScript 或 Kotlin**；只有遇到明确的进程调用、部署或性能问题时再考虑迁移。

### 3.2 Kotlin 智能能力：先验证，不要预设成功

截至本建议撰写时，JetBrains 已提供官方 Kotlin Language Server 以及 VS Code 扩展（Alpha），可以先将其作为标准 `.kt` 的分析基座。但它**并不直接识别 `.ktzh`**。

推荐进行三条技术路线的对比性小实验：

| 方案 | 做法 | 主要风险 |
|---|---|---|
| A：生成 `.kt` 镜像 | `.ktzh` 每次保存/编辑后生成标准 Kotlin 文件，并由已有 Kotlin LSP 分析 | 同步、跨文件索引、返回的位置和 URI 映射；生成文件被误改 |
| B：LSP 代理 | 在编辑器与 Kotlin LSP 之间转译文档及 LSP 消息 | 需要双向处理多类请求/响应，WorkspaceEdit 与 code actions 尤其复杂 |
| C：自有轻量语言能力 | `.ktzh` 自己实现高亮/片段/基础诊断，先不接完整 Kotlin 语义服务 | 补全、重构能力有限，但最容易稳定交付 |

**优先验证 A 与 C 的组合。** 只有当基础功能可用、需求明确后再投入 B。不要在未完成原型前断言 Kotlin LSP 一定可以无缝复用。

需要重点验证：

1. 中文关键字长度与英文关键字不同，source map 必须支持**双向范围映射**，而不只是单个错误点；
2. LSP/VS Code 的位置通常按 UTF-16 代码单元计，转译器可能使用 Python 字符索引或 UTF-8 字节偏移，必须定义统一转换规则；
3. `rename`、`codeAction`、`formatting` 可能返回对生成 `.kt` 的文本编辑，需要防止直接破坏原始 `.ktzh`；
4. `.ktzh` 与 `.kt` 混合工程、多文件符号引用、增量编辑、取消请求、不同步版本、并发更新，都必须纳入测试；
5. 中文保留字（例如 `值`）与合法标识符冲突，需要错误提示和词表规约，而非临时字符串替换。

### 3.3 不推荐现在做的事情

- 不从零实现文本编辑器、文件树、Git、终端、调试协议、插件市场；
- 不立刻创建独立 IDE 安装包；
- 不 fork Kotlin 编译器或维护私有 Kotlin IDE 插件分支；
- 不为了“更彻底中文化”一次翻译所有关键字和 Kotlin 标准库；
- 不直接把 DeepSeek/教师大模型的自然语言解释当作 AI 的真实执行轨迹。

## 4. 逻辑 AI 学习与推理调试器：真正值得自研的部分

传统 IDE 的断点、变量与堆栈视图无法完整表达我希望研究的学习流程。更重要的是：**所有可视化内容应来自引擎产生的结构化事件和状态，而非事后由 LLM 编造一段“看起来合理”的推理链。**

### 4.1 建议的事件协议（可逐步扩展）

初期定义稳定的事件信封：

```json
{
  "runId": "run-001",
  "eventId": "evt-017",
  "sequence": 17,
  "timestamp": "2026-11-02T10:00:00Z",
  "type": "hypothesis.proposed",
  "parentEventId": "evt-013",
  "data": {
    "hypothesisId": "h-5",
    "claimId": "c-12",
    "status": "unverified",
    "sourceRefs": ["source-9"]
  }
}
```

事件类型初步包括：

- `question.received`、`knowledge.retrieved`、`rule.applied`；
- `hypothesis.proposed`、`experiment.requested`、`experiment.completed`；
- `proof.checked`、`knowledge.updated`、`conflict.detected`；
- `policy.action_selected`、`run.paused`、`run.completed`。

每个事件应尽可能关联**概念、断言、证据、规则、证明、行动、成本**的稳定 ID，并记录所属知识库版本/快照。所谓 `proof.checked` 要区分“规则推导有效”“前提被外部证据支持”“整体结论在当前假设下成立”，不能把三者混成一个布尔值。

### 4.2 调试界面的最小功能

- **执行时间线**：按顺序观察真实的检索、规则命中、猜想、验证和知识更新；
- **证明依赖**：点击结论显示所依赖的前提、规则、来源和冲突；
- **候选面板**：查看产生了哪些假设，哪些被证伪、搁置或继续验证；
- **成本面板**：统计查询次数、展开节点数、规则执行次数、耗时及外部模型调用；
- **暂停与重放**：第一版优先“基于固定日志回放”；真实可暂停/可恢复执行要等引擎支持检查点和确定性恢复后再做。

不建议第一版就画复杂、会动的全量知识图谱。先做好列表、时间线、局部依赖图，保证每个展示的值都有对应事件或数据库记录。

### 4.3 与学习引擎的解耦

Kotlin 学习引擎只需要通过一个明确接口发布事件，例如：

```kotlin
interface 学习事件发布器 {
    fun 发布(事件: 学习事件)
}
```

事件可以先落 JSONL 文件，供编辑器读取和回放；稳定后再采用本地 WebSocket/HTTP 或其他 IPC。**不要为了第一版调试界面提前部署消息队列或微服务系统。**

## 5. 建议的语言和边界

| 组件 | 第一版技术 | 理由 |
|---|---|---|
| AI 知识类型 / 规则 / 学习循环 | Kotlin/JVM | 便于阅读、修改、测试；允许中文标识符 |
| `.ktzh` 转译器 | 保留已有 Python 版本 | 先利用已验证基础，避免不必要的重写 |
| IDE 语言扩展 | TypeScript | 直接使用 VS Code 扩展 API |
| 语义分析 | Kotlin 官方 LSP（先验证适配） | 复用 Kotlin 生态已有能力 |
| 推理事件协议 | JSONL + JSON Schema 起步 | 易检查、易回放、跨语言 |
| 学习调试视图 | VS Code Webview；可选简易前端 | 最小化 UI 实现成本 |
| 知识数据库 | 内存/SQLite 起步，后续 PostgreSQL | 调试器不应倒逼数据库提前复杂化 |
| 高性能热点 | 后续 Rust | 性能证据出现以后再迁移 |

建议保留**中文标识符 + 有限中文关键字 + 标准 Kotlin 可互操作**，避免把中文方言和 AI 推理引擎绑定。未来若放弃中文方言，也不应该导致核心 AI 无法运行。

## 6. 分阶段实施方案与验收条件

### 阶段 0：可行性尖峰实验（先做）

- 安装官方 Kotlin VS Code 扩展，验证当前机器上的 JVM/Gradle 工程工作流；
- 单独用 `.ktzh` → `.kt` 镜像验证**诊断、补全、跨文件跳转**三项能力；
- 做一条中英文长度变化、含 emoji/中文、跨行改动的 source map 往返测试；
- 给出“可复用 / 需要代理 / 暂不实现”的功能矩阵。

**验收**：提供可以录屏或自动化重现的最小仓库，不接受只有架构图的结论。

### 阶段 1：能实际写代码的中文 Kotlin 扩展

- 高亮、括号、输入片段、转译、编译、运行；
- 编译错误准确回到 `.ktzh`，报错片段与 caret 对齐；
- `.kt` 原有工作流不受影响；
- 对生成 `.kt` 实施只读/防误改策略。

**验收**：至少 10 个真实 Kotlin 源码样例和一组错误用例可以重复通过；生成文件与原文件一致性可自动检查。

### 阶段 2：选择性接入 Kotlin LSP

- 根据阶段 0 的实验结论按顺序开通：诊断、悬停、跳转、补全；
- 重命名、格式化、Quick Fix 默认保持关闭，直到双向 WorkspaceEdit 回写被充分测试；
- 增量编译、缓存、版本号与取消请求逐步补齐。

**验收**：不出现静默写坏中文源码；不能安全映射的编辑明确拒绝并提示原因。

### 阶段 3：AI 学习/推理事件调试器

- Kotlin 引擎输出结构化事件；
- VS Code 中显示时间线、证据与证明依赖、候选猜想和计算成本；
- 支持固定日志回放与同一次运行的结果对比。

**验收**：调试器显示的每一条推理步骤都能回指实际事件和证据，且能够定位错误知识如何影响后续结论。

### 阶段 4：独立 IDE 的必要性评估

只有当 VS Code 扩展已经满足基本需求，但**平台限制持续阻碍关键工作流**，或者需要面向非程序员发行一体化研究工具时，再研究 Code-OSS 定制或 Tauri + Monaco。此时已有的转译器、协议和调试视图应能直接复用。

## 7. 关键风险与应对

| 风险 | 影响 | 建议 |
|---|---|---|
| 中文化只是视觉偏好，没有提升理解 | 投入偏离主研究目标 | 用真实项目做阅读时间、理解正确率和错误率对照实验 |
| Kotlin LSP Alpha 兼容性变化 | 智能功能不稳定 | 隔离 LSP 适配器，锁定测试版本，允许降级为基础编辑能力 |
| Source map 不能处理编辑类操作 | 重命名/修复损坏源文件 | 严格双向映射、版本检查，不安全操作不开放 |
| 语言方言造成维护成本 | 生态割裂 | `.ktzh` 只作为前端，标准 `.kt` 作为编译产物；保持透明转换 |
| UI 展示的是模型编造的“思考” | 研究结论失真 | 只展示可审计事件；将模型自述明确标注为“模型声明” |
| 过度工程化 | AI 核心原型停滞 | 先做插件和事件回放，限制 IDE 研发范围 |
