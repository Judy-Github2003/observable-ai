# 技术评审：《中文 Kotlin 轻量 IDE 与逻辑 AI 学习调试器》v0.1

> 评审对象：`文档/中文Kotlin轻量IDE与逻辑AI学习调试器_技术建议_v0.1.md`
> 评审依据：《中文方言设计-v0.1》《认知陈述-v0.1》+ 本机实测 + 官方资料核对
> 标注：【已核实】官方文档或本机实测 ·【判断】我的主张 ·【待验证】需要实验

---

## 零、结论（三句话）

1. **「VS Code 扩展优先、不自研 IDE」我同意，而且比文档自己更有把握**——因为官方 `kotlin-lsp` 的能力比文档假设的强，连 rename 和 format 都有。
2. **但文档漏了一件比 LSP 更影响日常使用的事：Kotlin 代码本身的断点调试。** 而它的解法极便宜，已实测可行。
3. **A（生成镜像）与 B（LSP 代理）的定位反了。** A 应该是尖峰实验，B 应该是目标架构；把 A 当过渡会留下双份真相的技术债。

## 一、先更正我自己的一个判断

《认知陈述》里 P3 我写的是「IDE 是硬墙，我没找到旁路，但不排除它存在」。**旁路存在，我的判断要改。**

【已核实】`Kotlin/kotlin-lsp` 是 JetBrains 官方项目，Alpha 状态，基于 IntelliJ IDEA 和 IntelliJ Kotlin 插件实现，官方 VS Code 扩展 ID 为 `JetBrains.kotlin-server`。已支持：

| 能力 | 状态 |
|---|---|
| 补全 | ✅ IntelliJ 引擎 |
| 诊断 + 快速修复 | ✅ 但**只有英文**（见第四节） |
| 语义高亮 | ✅ |
| 重命名重构 | ✅ |
| 代码格式化 | ✅ |
| 悬停 / 文档跳转 / 调用层级 / 折叠 | ✅ |
| 构建系统 | Gradle、Maven；AGP 实验性；KMP 未来支持 |
| **调试** | ❌ 功能列表里没有 |

**但有一条决定性约束，文档没提：**

> 该服务器「基于 IntelliJ IDEA 最新版本以及 JetBrains Air 和 Fleet 产品的专有部分，因此**部分闭源**」，仓库是**只读镜像，不接受直接贡献**。

这条约束应该写进设计第 0 条，因为它一次性砍掉了整类方案：

- 「教 LSP 认识 `.ktzh`」——不可能，改不了服务器；
- 「让 LSP 的诊断输出中文」——不可能，字符串在闭源二进制里；
- 「提 PR 修它的编码问题」——不可能。

所以 P3 修正为：**墙还在，但墙上开了个门，门只通向标准 Kotlin，不通向 `.ktzh`。** 所有中文支持必须做在 LSP 外面。

## 二、我同意的五条

1. **不自研 IDE 内核、不 fork 编译器。** 同意，而且理由比文档给的更硬：kotlin-lsp 闭源，你连 fork 的选项都没有。
2. **阶段 0 必须交付可重现仓库，「不接受只有架构图的结论」。** 这是全文最有价值的一句话，建议提到文档最前面当总纲。
3. **UTF-16 位置单位警告。** 真实存在。LSP 默认按 UTF-16 code unit 计位；中文在 BMP 内是 1 个单位，emoji 和 CJK 扩展 B 区是 2 个；Python 用的是码点索引。三者混用必出 off-by-N。
4. **rename / format 默认关闭，直到 WorkspaceEdit 往返验证通过。** 对。这两个操作是唯一能静默写坏源文件的东西。
5. **调试器只展示可审计事件，拒绝 LLM 事后编造推理链。** 这是全文最有研究品味的部分，应当保留为项目铁律。

## 三、最大遗漏：断点调试

文档通篇没有回答一个问题：**我在 `.ktzh` 里按下 F5，断点停在哪？**

kotlin-lsp 不提供调试。VS Code 里 Kotlin/JVM 调试只能靠 JVM 调试器（JDWP）+ 源码路径映射。而这里有一个几乎免费的解法：

【已实测】转译器**行号严格 1:1 保持**（`演示.ktzh` 27 行 → `演示.kt` 27 行）。原因很简单：关键字替换和标点映射从不增删换行。

推论：

- 断点行号可以直接复用，**不需要 SMAP、不需要 JSR-45、不需要自定义调试适配器**；
- 只需要把「生成文件路径」映射回「`.ktzh` 路径」（一个 `sourceFileMap` 级别的工作量）；
- 代价只有列号对不上——而调试器基本不用列号。

**这条应该进阶段 1，不是阶段 3。** 它比补全更决定「我能不能真的每天用它」：写代码可以没有补全，但研究推理系统不能没有断点。

## 四、三处技术判断需要修正

### 4.1 A 与 B 的定位反了

| | A：生成镜像 | B：LSP 代理 |
|---|---|---|
| 上手速度 | 快 | 慢 |
| 只读智能 | 能给 | 能给 |
| **编辑智能** | **永远给不了** | 能给 |
| 真相源 | 双份（磁盘 `.kt` + 编辑中 `.ktzh`） | 单份（`.ktzh`） |
| 技术债 | rename 写进生成文件、下次转译被丢弃 | 一次性投入 |

A 的结构性缺陷是：**rename/format 产生的 WorkspaceEdit 落在生成文件上，下一次转译就把它冲掉了。** 所以 A 永远只能给「只读智能」，不可能长成编辑器。把它当过渡，等于先建一个注定要拆的东西。

而 B 的难度被文档高估了，因为转译器是**纯词法**的：

【已实测】半截代码 `函数 测试() { 如果 (` 能正常转译，exit 0，输出 `fun 测试() { if (`。LSP 本来就是为「输入到一半」设计的，两边天然兼容——不需要「保存后生成」，可以每次请求时在内存里转译。

**建议：A 只用于阶段 0 证明 kotlin-lsp 在本机可用；产品形态直接按 B 做，且第一版只代理四类请求**（diagnostics / hover / definition / completion），编辑类请求一律明确拒绝并提示原因。

### 4.2 「每次保存/编辑后生成」不够快

补全请求要在击键后 ~100ms 内返回。当前转译器是 Python 子进程，每次启动 50~100ms——光启动就吃掉预算。

改法不是重写成 TypeScript（文档这点判断对），而是**把转译器常驻化**：一次启动，用 stdin/stdout 收发 JSON-RPC。改动是一个循环的量级，能完整保住已有实现。

同时改触发模型：**按「请求」触发，不按「保存」触发**，转译结果只进内存不落盘。

### 4.3 中文化诊断这条路被闭源堵死了——文档的隐含假设不成立

文档第 3.1 节把「把编译诊断定位到原始 `.ktzh`」当作第一阶段的卖点。但这里有两个诊断源，性质完全不同：

| 诊断源 | 语言 | 能否中文化 |
|---|---|---|
| kotlinc 编译输出（你自己的流程） | 英文，但可控 | ✅ 可以包一层映射 |
| kotlin-lsp 实时诊断（红波浪线） | 英文，闭源 | ❌ 改不了 |

所以编辑器里会出现**两套语言不一致的诊断**：保存时编译报中文，击键时波浪线是英文。这不是 bug，是架构约束。

要么接受，要么第一阶段就不接 LSP 诊断、只用自己的编译诊断（一致性优先）。**这个取舍文档没有意识到，但它会直接决定第一版的手感。**

## 五、一条可能改变项目形态的建议

文档第 4 节的原则我完全同意：*「所有可视化内容应来自引擎产生的结构化事件和状态，而非事后由 LLM 编造」*。

我想把它推进一步：**如果你的目标是「读懂每一个知识对象和推导步骤」，那知识本身不该是 Kotlin 代码。**

用中文 Kotlin 写规则，得到的是两头不靠：

- 作为**代码**：中文关键字在整个生态里是孤儿（无补全、无搜索、无 StackOverflow、无 LLM 训练数据）；
- 作为**数据**：它是代码，不能查询、不能 diff、不能被通用工具检视、不能做增量推理。

而「概念 / 断言 / 证据 / 规则 / 证明」本质上是**数据**。用中文可读的规则 DSL（YAML、JSON 或自定义文本格式）+ 一个渲染器，比用中文 Kotlin 写更接近你的目标，而且**完全绕开 IDE 问题**。

中文方言更该用在**引擎代码**上——推理循环、搜索策略、调度、缓存，那些是真代码，需要断点、需要类型、需要重构。知识库那部分应该是可检视的数据。

如果这条成立，优先级会变：**「规则 DSL + 追踪视图」上升，「中文 Kotlin IDE」下降为主力开发工具的一个便利项。** 这也正好回答文档的第 6 问。

## 六、我建议的阶段计划与工作量

| 阶段 | 内容 | 验收 | 估时 | 停止条件 |
|---|---|---|---|---|
| 0 尖峰 | kotlin-lsp 在本机（Windows / Gradle / Kotlin 2.4）能否启动并索引；镜像方案下 diagnostics、hover、definition 是否可用；**是否接受非标准目录结构** | 可重现仓库 + 功能矩阵 | 3–5 天 | 本机起不来或索引不了 → 退回纯自研（C 方案），放弃 LSP |
| 1 最小可用 | 语法高亮（含中文关键字 TextMate 作用域）、常驻转译器、编译运行、**断点调试**、错误回映射含片段重绘 | 10 个样例 + 错误用例可重复通过；能在 `.ktzh` 里断点 | 2–3 周 | — |
| 2 只读智能 | 代理 diagnostics / hover / definition / completion | 位置映射无 off-by-N；无法映射时降级而非报错 | 3–4 周 | 位置映射 bug 率 > 5% → 只保留 hover |
| 3 编辑智能（可选） | rename / format 的双向 WorkspaceEdit | 绝不静默写坏源文件 | 不设期限 | 做不完就永久关闭，不影响使用 |
| 4 追踪视图 | 事件协议（先落 JSONL）+ 时间线/依赖/候选/成本面板 | 每条推理可回指事件 | 4–8 周，可与 1–3 并行 | — |

**关键排序：阶段 3 可选，阶段 1 的调试不可省。**

另外提醒一个物理约束：kotlin-lsp 是 IntelliJ 内核的 JVM 服务器，启动和索引就是十秒到几十秒、内存 1GB 量级。**「轻量 IDE」这个说法在接入它之后就不成立了**——轻的是编辑器，重的是语言服务。这不影响方案成立，但会影响你对「轻量」的预期。

## 七、如果只做三件事

1. **转译器常驻化 + 行号保持 → 断点可用**（约 1 天，已验证前提成立）
2. **TextMate 语法 + 半截代码容错**（约 2 天，容错已验证）
3. **错误回映射的片段重绘**（约 1 天，修掉 caret 错位的已知缺陷）

这三件做完，「这套东西能不能日常用」就有答案了，而且**完全不依赖 kotlin-lsp 是否稳定**。这比先啃 LSP 代理更划算——因为它们的失败概率低得多。

## 八、对文档第 6 问的直接回答

> 中文化关键字真的比中文命名、中文错误信息、AI 推理调试器更重要吗？

**不更重要，而且成本高一个数量级。**

| 项 | 成本 | 收益确定性 |
|---|---|---|
| 中文命名规范 | 0（今天就可用） | 确定，但采用率未验证 |
| 中文错误信息 | 1–2 天 | 立竿见影，不需架构 |
| AI 推理调试器 | 这是研究本身 | 不能外包 |
| 中文关键字 | 3 个月 + 持续维护 | **未验证** |

顺序应该是：**错误信息 → 命名规范 → 调试器 →（有剩余预算再做）关键字**。

反过来说，给自己设一个时间盒：**如果三周内做不出「能在 `.ktzh` 里断点调试」的最小系统，就承认这条支线失败，把精力收回引擎。** 这不是悲观，是把不可证伪的投入变成可停止的投入。

## 九、需要立刻做的验证（都能在一天内出结论）

1. 装 kotlin-lsp，在一个最小 Gradle 项目上确认它能启动、能补全、能跳转——**这是整个方案的地基，不过就全盘改路线**。
2. 把 `演示.ktzh` 转译后放进 Gradle 源码集，用 JDWP 挂 VS Code，确认断点行号对得上（行号 1:1 已实测，剩路径映射）。
3. 喂一个 2000 行的 `.ktzh` 给转译器，测单次耗时——决定是否需要常驻化（大概率需要）。
