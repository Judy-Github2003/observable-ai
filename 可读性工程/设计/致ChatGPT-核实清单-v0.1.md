## 一、需要你核实的事实（我查不到，或需要更权威来源）

> 每条请标注【已确认】/【需要实测】/【不确定】。**不确定就写不确定，不要用「一般来说」。**

**Q1｜kotlin-lsp 能否在非 Gradle / 非 Maven 的目录里工作？**
比如一个只有几个 `.kt` 文件 + 一个 JDK 的文件夹，能不能获得补全和跳转？还是必须有一个可被它识别的构建模型（Gradle/Maven）才能建立索引？
→ 这决定用户的工程前置成本，也决定「生成镜像目录」要不要挂进 Gradle source set。

**Q2｜它是否支持 LSP 3.17 的 `positionEncoding` 协商（utf-8 / utf-16 / utf-32），还是固定 UTF-16？**
如果可协商成 UTF-8，位置换算的复杂度会下降一个量级（Python 侧直接按字节走）。

**Q3｜它的跨文件符号索引，是否只来自磁盘上的文件？**
换句话说：如果我通过 LSP 的 `didOpen` 送进去一个**磁盘上不存在**的 URI（比如 `file:///proj/src/Main.kt`），它能提供跨文件解析，还是只能提供本文档内的能力？

**Q4｜承上：如果索引只认磁盘，那么「纯代理」方案是否根本不成立？**
我的怀疑：要让 A 文件里的符号在 B 文件里被解析，`.kt` 必须真实存在于磁盘并属于源码集。
**如果这条成立，那 A 和 B 就不是二选一，而是必须组合**——磁盘镜像负责索引，代理负责位置与 URI 翻译。
请你明确：我的「B 是终点」是否过度简化了？正确的形态是不是「A 提供地基 + B 提供编辑体验」？

**Q5｜`workspace/didChangeWatchedFiles` 与增量索引的成本如何？**
每次击键都重写镜像文件会不会触发全量重索引？有没有更合适的同步机制（比如只在保存时落盘、请求时走内存）——但那样又和 Q3 冲突。请指出这对矛盾的正确解法。

**Q6｜2026 年 11 月，VS Code 里的 Kotlin 调试现状是什么？**
是仍然依赖 JVM 调试器（JDWP）+ 某个 Java 扩展，还是已经有官方 Kotlin 调试适配器？JetBrains 的 VS Code Alpha 路线图里，调试在不在近期计划内？

**Q7｜如果行号 1:1 保持，断点映射需要做到什么程度？**
我的设想：`.ktzh:12` 的断点在 JVM 侧是 `演示.kt:12`，只需一个路径映射（`sourceFileMap` 或等价机制）就能让 VS Code 打开 `.ktzh` 并高亮第 12 行。
请判定：这对 Kotlin 是否成立？`sourceFileMap` 在 vscjava 的调试器里对 Kotlin 是否有效？有没有更可靠的替代（自定义 debug adapter / `sourcePaths` / 生成 SMAP）？

**Q8｜kotlin-lsp 的格式化是否支持 range formatting（只格式化选区）？**
如果只支持全文，那对 `.ktzh` 基本无用——因为格式化全文会把生成文件改写，而我们无法安全回写。

## 二、我需要你反驳的架构判断

**Q9｜A 与 B 的定位**
我的判断：「A（生成镜像）永远给不了编辑智能，因为 rename/format 的 WorkspaceEdit 落在生成文件上，下次转译就被冲掉；所以 A 只能当尖峰实验，B 才是目标架构。」
请判定这个判断是否成立。如果成立，请说明为什么你上一版把它写成「先 A+C，B 以后再说」是合理的（还是其实不合理）。

**Q10｜Volar / Svelte 的虚拟文档方案，是不是可复用的先例？**
我认为 Vue 的 Volar 和 Svelte 的语言工具做的正是同一件事：把`.vue`/`.svelte` 映射成虚拟的 TS 文档，再把 LSP 的位置双向翻译。如果这成立，请给出**具体可复用的实现套路**（虚拟文档生成、source map 的 VLQ 编码、position mapping 的边界处理、哪些请求必须拒绝）。

**Q11｜WorkspaceEdit 回写的安全边界在哪？**
rename 返回的是一组 range。把这些 range 映射回 `.ktzh` 再重写，哪些情况必须拒绝？
我担心的是：字符串模板内部、注释内部、同名但不同作用域的符号、以及 rename 范围跨界于「中文关键字 → 英文关键字」的替换区。请给出一个可以写进代码的判定规则，而不是原则性提醒。

**Q12｜转译器常驻化的 IPC 选型**
我打算把 Python 转译器改成常驻进程，用 stdin/stdout 的 JSON-RPC 与 VS Code 扩展通信。
请判定：这个选型在 Windows 上有什么坑（编码、缓冲、进程回收、僵尸进程）？单次转译 <5ms 是否现实（文件规模 2000 行）？有没有更简单的方案（比如直接嵌一个 WASM 版本）？

## 三、战略与先例

**Q13｜有没有生产环境真的在用中文关键字的案例？**
不是教学、不是玩票、不是个人项目。如果有，请给出名字和它活下来的原因；如果没有，请直接说没有——这个否定答案对我的判断很重要。

**Q14｜「知识作为数据 + 中文可读 DSL」有没有 prior art？**
我的主张是：概念/断言/证据/规则本质是数据，用中文 Kotlin 写是两头不靠；更好的载体是中文可读的规则 DSL（Datalog / N3 / 自定义文本）+ 渲染器。
请评价：这个主张是否成立？如果成立，你建议用哪种载体（Datalog 变体？属性图？自定义 s-expression？），理由是什么？如果已经有成熟的「中文可读规则格式」先例，请指出。

**Q15｜中文在代码里的可读性，有没有实证研究？**
我提出一个反向假设：等宽字体下中文占两格，`如果 (年龄 > 18)` 比 `if (年龄 > 18)` 宽约 40%，行长增加可能**降低**扫读效率——即中文关键字可能反而更难读。
请给出：有没有 CJK vs ASCII 标识符/关键字的阅读实验数据？如果没有，请说明该实验应该怎么设计（被试内设计？counterbalanced？样本量？指标？）。

**Q16｜Excel 本地化函数名这个先例，我的描述准确吗？**
我说：微软做了本地化函数名（德语 `SUMME`），结果是文件内存储英文、界面显示本地化、跨语言复制粘贴炸掉，成为公认设计债，之后成熟系统转向「规范形式存储 + 表现层本地化」。
请核实或修正。如果这个先例被我误用了，请直接指出。
