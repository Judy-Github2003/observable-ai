# 中文 Kotlin 方言 · 设计说明 v0.1

> 状态：机制已验证（可编译、可运行、报错可回映射）。批次一词表是占位版本，等真实语料定稿。
> 编译器版本：kotlinc-jvm 2.4.0（IntelliJ 自带）

---

## 一、一句话结论

**关键字可以按文件开启的中文方言来做，中文标点可以按词法白名单做；但不要做成「全局软关键字」，也不要一次翻全量。**
批次一先翻 13 个语法骨架词，机制已经跑通；词表顺序应该由真实代码语料统计决定，而不是凭直觉。

---

## 二、实测基线

用 kotlinc-jvm 2.4.0 直接编译三个文件，不经过任何工具：

| 用例 | 内容 | 结果 |
|---|---|---|
| `01_标识符.kt` | `fun 问候(名字: String)`、`val 完整句子` | ✅ exit 0 |
| `02_中文关键字.kt` | `函数 问候(...)`、`值`、`返回` | ❌ `Expecting a top level declaration` ×4 |
| `03_全角标点.kt` | `fun 问候（名字: String）` | ❌ `Expecting '('` |

三条结论：

1. **中文标识符是免费的**，不需要任何改动，字节码层也无障碍（class 文件只禁 `. ; [ /`）。
2. **中文关键字和全角标点是真的不支持**，卡在词法层。
3. 用例 02 里**一个错误触发了 4 条报错**——错误恢复质量是后续必须盯的指标，不是附带项。

## 三、核心决策：按文件开启的「方言」

### 3.1 从产生式看软关键字的真实机制

Kotlin 的语法定义（ANTLR）里，所有软关键字和修饰符都被显式列进 `simpleIdentifier`：

```
simpleIdentifier
    : Identifier
    | ABSTRACT | ANNOTATION | BY | CATCH | COMPANION | CONSTRUCTOR
    | ... | WHERE | FIELD | PROPERTY | RECEIVER | PARAM | SETPARAM
    | DELEGATE | FILE | EXPECT | ACTUAL | CONST | SUSPEND | VALUE
    ;
```

这告诉你两件事：

- 软关键字**在词法层就是普通标识符**，靠语法层的白名单位置重新解释；
- 硬关键字（`IF`/`FOR`/`WHILE`/`RETURN`…）**不在**这个列表里，所以它们永远不能被当标识符。

### 3.2 为什么不能把中文词塞进 `simpleIdentifier`

技术上可行，但会立刻撞上真歧义：

```kotlin
如果(x) { 打印(x) }
```

这**本来就是合法 Kotlin**——调用一个名叫 `如果` 的函数，并传一个尾随 lambda。一旦 `如果` 同时是 `if` 的候选，语法上无法判定，只能靠 lookahead 加一堆特例规则，而这些规则会随每个新词线性增长，还会污染错误恢复。

**结论：向后兼容和语法无歧义不可兼得。** 要么放弃兼容（硬关键字，存量代码可能挂），要么引入开关。选开关。

### 3.3 方言开关的三个后果

| 后果 | 说明 |
|---|---|
| 语法无歧义 | 方言文件里中文词是硬保留字，`如果(x){}` 不可能是函数调用 |
| 兼容性是白拿的 | 不声明方言的文件，词法根本进不到中文关键字分支 |
| 代价：不能中英混用 | 一个文件一种语法。这反而更干净——混排文件的可读性本来就是幻觉 |

### 3.4 方言内保留「双轨」

方言文件里，英文关键字**仍然合法**。原因很实际：批次一还没翻译 `package` / `import` / `class`，不双轨就写不出完整文件。

双轨不破坏无歧义性——两组词各管各的，互不干扰。

### 3.5 开启方式

| 实现路线 | 开关 |
|---|---|
| 转译器（当前已实现） | 文件扩展名 `.ktzh` |
| 改编译器 | 文件注解 `@file:中文` 或参数 `-Xzh-dialect` |

## 四、批次一词表（13 个）

| 中文 | Kotlin | 语法位置 | 产生式依据 | 标识符冲突风险 |
|---|---|---|---|---|
| 函数 | `fun` | 前缀 | `functionDeclaration: FUN` | 低 |
| 值 | `val` | 前缀 | `propertyDeclaration: VAL` | **高**（`val 值` 很自然） |
| 变量 | `var` | 前缀 | `propertyDeclaration: VAR` | 低 |
| 如果 | `if` | 前缀 | `ifExpression: IF` | 低 |
| 否则 | `else` | 前缀 | `ifExpression` / `whenEntry: ELSE` | 低 |
| 只要 | `while` | 前缀 | `whileStatement: WHILE` | 低 |
| 遍历 | `for` | 前缀 | `forStatement: FOR` | 低 |
| 当 | `when` | 前缀 | `whenExpression: WHEN` | **中** |
| 在 | `in` | 中缀 | `inOperator: IN` | **中** |
| 返回 | `return` | 前缀 | `jumpExpression: RETURN` | 低 |
| 真 | `true` | 字面量 | `BooleanLiteral` | 低 |
| 假 | `false` | 字面量 | `BooleanLiteral` | 低 |
| 空 | `null` | 字面量 | `NullLiteral` | 中 |

### 三条选词原则

1. **只收前缀位或中缀位的词**。`when`/`try`/`if` 这类只要不引入句尾标记词，翻译成本就是线性的；一旦要「当…时」「尝试…捕获…」，就变成改产生式。
2. **两个字起步**。单字（`值`、`类`、`当`）与变量名撞车概率高一个量级。
3. **不碰类型名和 stdlib 函数**。`String`→`字符串`、`listOf`→`列表` 是库别名层的事，和语法层解耦，可以晚做、可以随时改。

## 五、刻意排除的词，以及为什么

| 词 | 问题 | 处置 |
|---|---|---|
| `类` / `对象` | 单字 + 高频；`val 类 = ...` 会挂 | 批次二，配 `此`（this）一起引入 |
| `当…时` | `while` 若译「当」，与 `when` 的「当」冲突 | `while` 用「只要」，`when` 用「当」 |
| `最终` | `final` 和 `finally` 都想要这个词 | 先定 `finally`→「最后」，`final`→「不可覆写」，否则会陷入翻译争论 |
| `是` / `作为` | `是` 是最常见的中文变量字，硬保留代价大 | 批次三，且要同时给「不是」「安全作为」 |
| `包` / `导入` | 不影响可读性，但缺了写不出完整文件 | 批次三；在此之前靠双轨 |

**翻译争论要有裁决规则**：一个词进不进词表，看三条——词频、冲突风险、是否需要改产生式。三条都不占优的词，宁可不翻。

## 六、中文符号映射

独立于关键字，纯词法层，**显式白名单**：

| 中文 | ASCII | 用途 |
|---|---|---|
| `（` `）` | `(` `)` | 参数、条件 |
| `，` `、` | `,` | 分隔 |
| `：` | `:` | 类型标注 |
| `；` `。` | `;` | 语句终止 |
| `？` | `?` | 可空、Elvis、三目 |
| `！` | `!` | 取反 |
| `＝` `＋` `－` `＊` `／` `％` | `=` `+` `-` `*` `/` `%` | 运算 |
| `＜` `＞` `＆` `｜` `＠` `＃` `～` | `<` `>` `&` `\|` `@` `#` `~` | 其余 |
| `　` | 空格 | 全角空格 |

### 三条硬规则

1. **只在字符串/字符/注释之外生效**。否则 `"你好，世界"` 会被改坏——这是最容易踩的坑。
2. **不用 NFKC 全量归一化**。NFKC 会把 `①`→`1`、`㎏`→`kg`、`ﬁ`→`fi`，映射范围不可控，也没法审计。白名单只有 20 来条，错了能查。
3. **中文引号 `“”` 不映射**。映射成 `"` 会让「引号开始的散文」被当成字符串开头，风险大于收益，v0.1 直接排除。

## 七、参考实现

```
可读性工程/
├─ 工具/
│  ├─ ktzh.py          转译器：.ktzh → .kt，带逐字符 source map
│  └─ 词频统计.py       用语料给关键字排优先级
├─ 示例/
│  └─ 演示.ktzh         中文方言演示源码
├─ 验证/
│  ├─ 基线/             三个对照用例（证明哪层免费、哪层不支持）
│  ├─ 错误示例/         报错回映射、保留字拦截的用例
│  └─ build/            转译产物
└─ 文档/kotlin-docs/    24 篇 Kotlin 语言参考（370 KB）
```

### 转译器做了什么

1. 一个状态机跟踪 `code / string / raw / char / line_comment / block_comment`，支持嵌套块注释和 `${...}` 模板表达式。
2. 代码态里做中文关键字（最长优先）和全角标点替换；其余状态原样输出。
3. 每输出一个字符，记录它来自源文件的哪个偏移——编译器报回去的行列再映射回来。
4. 保留字出现在标识符位置（前面是 `val`/`fun`/`.` 等）时**在转译期直接报错**，而不是产出 `val val` 让编译器去骂人。

### 怎么用

```powershell
# 转译
python 工具\ktzh.py build 示例\演示.ktzh -o 验证\build\演示.kt

# 转译 + 编译 + 报错回映射
python 工具\ktzh.py check 示例\演示.ktzh --kotlinc <kotlinc.bat> --java-home <jbr>

# 语料词频
python 工具\词频统计.py <源码目录>
```

### 已知限制

1. 报错回映射后，附带的那行代码片段仍是**转译后**的文本，caret 位置会错位（不影响行列号，只影响显示）。
2. `.ktzh` 文件在 IntelliJ 里没有补全和重构——转译器路线绕不过 IDE，这是它的天花板。
3. 方言文件里不能用保留字做标识符（`val 值` 会报错），需要团队约定。
4. 目前不做增量构建集成（每次全量转译）。

## 九、语料统计：词表不该凭直觉定

用 `kotlin-stdlib-sources.jar` 做第一版语料：380 个文件、48,943 非空行、60,570 次关键字出现。

| 覆盖目标 | 需要翻译的词数 |
|---|---|
| 47.9% | 批次一的 13 个（**手选的，不是最优解**） |
| 81.7% | 词频前 15 个 |
| 87.0% | 词频前 19 个 |
| 92.6% | 词频前 25 个 |
| 95.4% | 词频前 30 个 |

**两个反直觉的发现：**

1. **批次一并非最优。** `when` 只占 0.3%、`while` 0.5%，而 `this` 占 6.9%、`class` 1.8%、`public` 12.7% 都没进。手选词表被「语法直觉」带偏了，真实代码里修饰符和 `this` 的密度远高于预期。
2. **`public` 排第 2**（12.7%），`internal` 排第 5（6.0%）。这说明如果目标是「读起来不像英文」，可见性修饰符的收益比 `when`/`while` 大得多。

**必须声明的偏差：** stdlib 是库代码，`public`/`internal`/`actual`/`expect`/`inline` 的密度天然远高于业务代码（它是多平台库，满屏 `expect/actual`）。**批次二的顺序必须用你们自己的代码库重跑一遍这个脚本再定。**

## 十、路线图

| 批次 | 内容 | 关卡 |
|---|---|---|
| 一（已实现） | 语法骨架 13 词 + 全角标点 | 本文件 |
| 二 | 高频修饰符 + `此`/`类`/`对象`，按真实语料排序 | 语料统计定稿 |
| 三 | 结构词：`包`/`导入`/`接口`/`枚举`/`尝试`/`捕获`/`最后`/`抛出`/`是`/`作为` | 需要定句尾标记策略 |
| 四 | stdlib 别名层（`列表`/`打印`/`过滤`），纯库不改语法 | 需要拉 stdlib API 清单 |

**每批的验收标准（三条，缺一不可）：**

1. 存量 `.kt` 文件零回归；
2. 新增词不引入语法歧义（方言内可判定）；
3. 报错位置能映射回中文源码。

## 十一、如果要做进编译器，改动清单

不是为了现在做，是为了知道成本边界：

| 层 | 文件/机制 | 改动 |
|---|---|---|
| 词法 | `Kotlin.flex` / `KtTokens` | 加中文 token，或加方言分支 |
| 词法 | 全角标点归一化 | 在 `_KotlinLexer` 出口做白名单替换 |
| 语法 | `KotlinParsing` | 每个中文关键字加判定 + 错误恢复集合 |
| PSI | `KtNodeTypes` / `KtPsiFactory` | 从 AST 重新生成代码的路径要输出中文，否则重构会退化成英文 |
| 诊断 | `KtDiagnosticFactory` | 中文方言下的报错文案 |
| 多后端 | JVM / JS / Native / Wasm | 标识符无需改；但要各跑一遍回归 |

**真正的地板仍然是 IDE**：IntelliJ 的 Kotlin 插件随 IDE 分发、与编译器版本绑定，你没法让团队用你的分支还保留补全和重构。

## 十二、明确不做的事

- 不做「全局生效的中文关键字」——会破坏存量代码，且无解地引入歧义。
- 不做中文类型名和中文 stdlib 函数的语法层改造——那是库别名层，解耦收益更大。
- 不在 v0.1 引入句尾标记词（`当…时`、`尝试…结束`）——那是语法设计问题，需要单独一轮。
- 不追求「关键字全译」——语料显示前 25 个词就到 92.6%，剩下的长尾收益递减而冲突风险递增。
