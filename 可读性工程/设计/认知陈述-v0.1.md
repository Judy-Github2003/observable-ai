# 认知陈述：中文可读性工程 / Kotlin 中文化

> 用途：供第三方（人或模型）审阅、反驳、补充。
> 撰写时间：2026-11-02。作者立场：支持探索，但对「翻译关键字」这条路的性价比持怀疑。
> 标注约定：【实测】本机验证过 ·【文档】出自官方文档/语法定义 ·【推断】由证据推演 ·【判断】价值或策略主张，可被反驳 ·【存疑】我没有把握

---

## 一、我怎么定义这个任务

**表层定义**：让 Kotlin 支持中文关键字和中文符号，从而「用中文写 Kotlin」。

**我认为的真实定义**：降低中文母语者阅读和编写代码时的认知负荷。

这两个定义**不等价**，而且差距很大。如果按表层定义，任务的成功标准是「这段中文代码能编译」——那是词法问题，几个月能做完。如果按真实定义，成功标准是「一个中文母语的新人读这段代码更快、犯错更少」——那是语言设计、工具链、团队习惯的复合问题，而且**没有人验证过中文关键字在其中占多大权重**。

**我判断这个项目最大的风险**：它很容易滑向「做一个中文编程语言 demo」——技术上很爽，演示效果很好，但离「可读性工程」越来越远。判断标准很简单：如果三个月后的成果是一段能跑的中文 Kotlin，而不是一个团队真的在用它维护代码，那就是滑了。

## 二、事实层

这些是有证据的，不涉及价值判断。

| # | 事实 | 证据强度 |
|---|---|---|
| F1 | Kotlin 原生支持中文标识符（`fun 问候()`、`val 完整句子`），编译通过、字节码正常 | 【实测】kotlinc 2.4.0，exit 0 |
| F2 | 中文关键字不支持，报 `Expecting a top level declaration` | 【实测】 |
| F3 | 全角标点不支持，`fun 问候（...）` 报 `Expecting '('` | 【实测】 |
| F4 | JVM class 文件对标识符只禁 `. ; [ /` 四个字符，中文无阻碍 | 【文档】JVM 规范 |
| F5 | Kotlin 软关键字在词法层就是普通标识符，由语法层的 `simpleIdentifier` 白名单重新解释 | 【文档】ANTLR 产生式 |
| F6 | 硬关键字不在 `simpleIdentifier` 里，因此永远不能当标识符 | 【文档】 |
| F7 | 关键字总量 79 个：31 硬 + 19 软 + 29 修饰符 | 【文档】keyword-reference |
| F8 | 一个中文语法错误会连带触发多条报错（实测一个错误 → 4 条） | 【实测】 |
| F9 | stdlib 源码语料：380 文件 / 48943 行 / 60570 次关键字；词频前 15 覆盖 81.7%，前 25 覆盖 92.6% | 【实测】我跑的统计 |
| F10 | `public` 在 stdlib 里是第 2 高频关键字（12.7%），`this` 第 4（6.9%），`when` 0.3% / `while` 0.5% | 【实测】同上 |
| F11 | 中文标识符在中文开发者社区里**允许但实际使用率很低**（生产代码中罕见） | 【推断】观察，无量化数据 |

F11 是我认为被严重低估的一条，见第五节。

## 三、判断层：八个可被反驳的命题

### P1｜「翻译工作」只对标识符和标点成立，对关键字不成立
【判断】置信度 85%

词表只有 79 个词，看起来是翻译。但前缀词（`fun`/`if`/`return`）能直译，结构词（`when`/`try`/`object :`）的中文自然语序要求句尾标记词（`当…时`、`尝试…结束`），那是改语法产生式，不是改词表。

**如果这条错了会怎样**：如果结构词不加句尾标记也能被接受（即直译的可读性已经够），那工作量会降一个数量级。这是可以实测的——让中文母语者读「直译版」和「加标记版」，看哪个更顺。

### P2｜语法无歧义与全局向后兼容不可兼得，因此必须文件级方言
【判断】置信度 80%

`如果(x) { }` 在今天就是合法的「调用名为 `如果` 的函数并传尾随 lambda」。一旦 `如果` 同时是 `if` 的候选，语法上无法判定。

**最脆弱的环节**：这条推理假设了「无法用 lookahead 解决」。Kotlin 自己就用 lookahead 处理 `by`/`where`/`field`。所以严格说 P2 应表述为「消歧规则的数量会随词表线性增长且污染错误恢复」，而不是「不可能」。我的置信度因此从 90% 下调到 80%。

### P3｜最大的障碍不是编译器，是 IDE
【判断】置信度 90%（作为「工程现实」的判断，不是技术不可能）

改编译器前端做出 demo 是 2~4 人月的事。但 IntelliJ 的 Kotlin 插件随 IDE 二进制分发、与编译器版本强绑定，团队装上你的分支就失去补全和重构。没有团队会接受这个交换。

**这条错了会怎样**：如果存在某种 LSP / 插件的旁路方案让 IDE 跟随自定义语法，整个成本结构就变了。我没找到这样的方案，但我不排除它存在。

### P4｜可读性的瓶颈不在关键字
【判断】置信度 70%（价值判断，无实验数据）

我认为下面三件事的收益大于 79 个关键字：
1. 中文领域词汇表 + 命名规范（`订单.是否已支付` vs `order.isPaid`）
2. 中文诊断信息（包一层编译器输出映射即可，不需要 fork）
3. stdlib 中文别名层（纯库，不改语法）

**这条最可能错**，因为它是纯主观排序。「读代码时到底卡在哪」应该做用户研究，而我没做。

### P5｜长尾关键字不值得翻
【判断】置信度 85%

语料显示前 25 个词覆盖 92.6%，剩下 54 个词只贡献 7.4%，但每个词的冲突风险和维护成本不降反升。

### P6｜历史项目失败于生态而非语法
【判断】置信度 75%

易语言（语法完全中文化，活下来了但生态封闭）、周蟒（中文 Python，已死）、文言（玩票性质）。共同点：语法都做到了，但没人给它写库、写工具、写教程、写招聘需求。

**反面证据**：易语言在特定领域（国内小工具开发）确实有真实用户群，说明「中文语法」在某些市场是有支付意愿的。我不确定这是否可复制到 Kotlin。

### P7｜Excel 的教训给出了架构答案
【判断】置信度 85%

微软给 Excel 做了本地化函数名（德语 `SUMME`），结果是文件内存储英文、界面显示本地化，跨语言复制粘贴炸掉，至今是设计债。之后成熟系统的统一做法：**工具链用规范形式，只在表现层本地化**。

这条直接支持「转译器 + source map」路线，而不是「改编译器」。

### P8｜上游化是唯一能长期存活的路径
【判断】置信度 70%

如果中文关键字最终要保留 IDE 支持，只有 JetBrains 官方做得到。可行的窄提案是「全角标点归一化」这类低风险、普适的改动，而不是中文关键字本身。

## 四、我的推理链，以及最脆弱的三环

```
F1 中文标识符免费
  → 所以「中文编程」的价值不能靠标识符证明
F2/F3 关键字和标点不支持
  → 所以必须有人改词法/语法层
P1 结构词需要句尾标记 → 改语法而非改词表
P2 歧义 → 必须文件级方言
  → 代价：一个文件不能中英混用
P3 IDE 是硬墙 → 自建分支不可交付
P7 架构答案 = 规范形式 + 表现层本地化
  → 转译器 + source map 是当前唯一可交付形态
  → 但它绕不过 IDE，天花板在此
```

**三个最脆弱的环节**：

1. **「歧义无法解决」** —— Kotlin 自己用 lookahead 处理软关键字，凭什么说中文不行？我只能退守到「成本线性增长」。
2. **「IDE 是硬墙」** —— 我没有穷举所有旁路方案。如果存在一个 LSP 层的解法，P3 就垮了，整条路线图要重画。
3. **「可读性瓶颈不在关键字」** —— 这纯粹是我的主观排序，没有任何用户研究支撑。整个项目的地基其实在这里，而它是空的。

## 五、反对我自己的最强论证

我必须把这条单独写出来，因为它比上面所有判断都更有说服力：

**中文标识符已经免费了三年，但生产代码里几乎没人用。**

`val 用户名` 从 Kotlin 1.0 起就合法，不需要任何改动、任何工具、任何成本。如果中文命名对可读性的收益真的那么大，市场早就用脚投票了。事实是没有。

这说明一个残酷的可能性：**中文在代码里的价值，不在「语法是中文」，而在「命名用的是本领域的中文词汇」。** 前者是可用性问题（已经解决），后者是习惯问题（工具解决不了）。

如果这个论证成立，那么「翻译关键字」的项目前提就是错的——它解决的是一个假想需求。而真正值得做的是「中文领域词表 + 命名规范」，那是完全不同的项目。

**我对这条论证的反驳（很弱）**：免费但没被采用，可能不是因为没价值，而是因为「混排很难看」——一个文件里中文标识符配英文关键字，视觉上是割裂的。如果关键字也中文化，整体感成立，采用率可能就上来了。这个反驳可以验证：做一个整体中文化的示例给人看，问他们愿不愿意用。

## 六、我明确不知道的

1. **中文关键字对母语读者的实际阅读增益有多大？** 没有实验数据。这是整个项目的地基，但据我所知没人测过。
2. **视觉密度问题**：等宽字体下中文占两格，`如果 (年龄 > 18)` 比 `if (年龄 > 18)` 宽约 40%。行长增加可能导致换行、降低扫读效率——**中文关键字可能反而降低可读性**。这个反向假设我没验证。
3. **协作成本**：中文关键字代码无法被搜索引擎和 LLM 有效辅助（StackOverflow 上没有对应问答），新人求助成本上升多少？
4. **这个项目的用户是谁？** 教学？国企/政务合规？非英语母语团队？我不知道，而这决定了完全不同的成功标准。
5. **Kotlin 官方是否可能做本地化**：我认为不会（语言本地化在现代语言设计里是共识性的反模式），但没有依据。

第 4 条我认为是最关键的分岔：如果是**教学场景**，转译器路线完全够用，IDE 缺失不重要，P3 失效。如果是**生产场景**，P3 直接封死。我不知道你们属于哪个。

## 七、如果只能先做一件事

**不是写编译器，是做一次阅读实验。**

给 20 个中文母语开发者两段等价代码（一段中文关键字、一段英文关键字），测：理解时间、理解正确率、主观偏好。

- 成本：2 天
- 收益：整个项目的优先级判断
- 判据：如果理解速度提升 < 15%，说明关键字不是瓶颈，P4 成立，项目应该转向命名规范和诊断本地化

我主张先做这个，不是因为保守，是因为**现在所有的计划都建在一个没被测过的假设上**。
